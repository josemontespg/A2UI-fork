How to Integrate A2UI into an Agent

Backend and agent developers can add A2UI UI generation to a TypeScript, Python, or Dart agent server so a language model streams validated interactive surfaces to clients and handles multi-turn user actions.

If you are building the client application instead, see How to Integrate A2UI into a Client. To share custom widgets beyond the built-in Basic catalog, see How to Define a Catalog, and for wire vs. compact DSL trade-offs see Swappable Inference Formats. Swift (A2UISwiftCore and A2UISwiftUI) targets client-side rendering rather than server-side agent generation.

Step 1: Install dependencies

Install the Agent SDK and Core SDK packages for your server language:

  • TypeScript
  • Python
  • Dart

Step 2: Configure A2uiGenerator, catalogs, and inference format

Create one A2uiGenerator when your server starts and share it across requests. Register every catalog the agent supports inside a CatalogConfig wrapper, starting with the built-in v1.0 Basic catalog and adding any domain-specific catalog.json files via CatalogConfig.fromPath (in TypeScript and Dart) or CatalogConfig.from_path (in Python).

By default, A2uiGenerator configures ExpressFormatFactory, which instructs the model to emit the compact <a2ui> inference format and compiles each statement into A2UI JSON messages. If your model or fine-tuned checkpoint writes raw A2UI JSON envelopes inside <a2ui-json> tags instead, pass DirectJsonFormatFactory (new DirectJsonFormatFactory() in TypeScript, DirectJsonFormatFactory() in Python, or const DirectJsonFormatFactory() in Dart).

  • TypeScript
  • Python
  • Dart

In Python, you can also compose reusable server-side component templates with @macro and expand them into Basic catalog primitives through MacroExpander (from a2ui.transformers.macros import MacroExpander, macro) so mobile and web clients render new composite layouts without a client release.

Step 3: Negotiate capabilities and build the system prompt

On every client request, read metadata.a2uiRendererCapabilities (or metadata.a2uiClientCapabilities for v0.9.1 clients) and negotiate an A2uiRequestProcessor for that caller’s supported catalogs.

How you manage RendererState depends on your UI lifecycle:

  1. Multi-turn canvas sessions keep one RendererState per conversation so later turns can update or delete surfaces created in earlier turns. Check acceptsState (accepts_state in Python) on each turn in case the client’s negotiated catalogs changed, and bind state to the request processor.
  2. Stateless chat turns omit state, validating each model response against a fresh RendererState so every turn creates its own self-contained surface.

Append processor.promptSnippet (processor.prompt_snippet in Python) to your agent’s role instructions before calling the language model:

  • TypeScript
  • Python
  • Dart
Wire format: inbound renderer capabilities metadata

Client renderers attach their supported capabilities in transport metadata (a2uiRendererCapabilities under "1.0" in v1.0, or a2uiClientCapabilities under "v0.9" in v0.9.1):

v1.0 renderer_capabilities.json ↗ v0.9.1 client_capabilities.json ↗
  • v1.0 (Candidate)
  • v0.9.1 (Active)

Step 4: Parse output, validate, and self-correct

A2uiRequestProcessor gives you two ways to turn model output into validated A2UI messages:

  1. Incremental streaming (openStream in TypeScript and Dart, open_stream in Python) feeds LLM token chunks into a stateful stream reader, heals progressive string keys such as text while tokens arrive, applies each emitted message to RendererState, and yields createSurface, updateComponents, updateDataModel, and deleteSurface messages as soon as they are ready.
  2. Whole-response validation with self-correction (parseResponse in TypeScript and Dart, parse_response in Python) checks a complete response inside an atomic RendererState transaction. If the model invents an unknown component, omits root, or writes a dangling child ID, RendererState rolls back every change from that turn and raises A2uiError, whose message you can feed back to the model for a retry.
  • TypeScript
  • Python
  • Dart

If your app runs both the agent and a local MessageProcessor inside the same TypeScript or Dart process, use StreamedAnswer (new StreamedAnswer(processor, {renderer}) in TypeScript or StreamedAnswer(processor, renderer: renderer) in Dart), which binds RendererState.of(renderer) directly so streamed surfaces mount without JSON serialization.

Wire format: Express output and compiled messages

With ExpressFormatFactory, the model writes a compact <a2ui> block using UAX #31 component identifiers (confirm_btn, confirm_label) and $/... data-model bindings:

The parser compiles that block into validated JSON messages ("version": "1.0" with {"@path": "..."} bindings in v1.0, or "version": "v0.9" with {"path": "..."} bindings in v0.9.1). During incremental openStream / open_stream reads, v1.0 emits createSurface with the initial root and dataModel followed by updateComponents deltas as remaining components arrive; when parsed whole via parseResponse / parse_response, v1.0 folds all initial components and data into createSurface:

v1.0 agent_to_renderer.json ↗ v0.9.1 server_to_client.json ↗
  • v1.0 (Candidate)
  • v0.9.1 (Active)

Step 5: Handle inbound actions, data models, and function RPCs

Clients send three main renderer_to_agent messages back to your server (plus rendererFunctionResponse if your agent invokes callRendererFunction):

  1. callAgentFunction (v1.0 only) invokes a backend catalog function via callFunction["@call"] and callFunction["args"]. Execute your backend logic directly and return agentFunctionResponse correlated by functionCallId (value on success, or error on failure) without an LLM round-trip.
  2. action reports a user UI event (name, surfaceId, sourceComponentId, context). When the surface was created with sendDataModel: true, read the synchronized surface data model from metadata.a2uiRendererDataModel.surfaces[surfaceId] (metadata.a2uiClientDataModel.surfaces[surfaceId] in v0.9.1) and include both in the next LLM turn so the model can update "order_summary" in place.
  3. error reports a client-side VALIDATION_FAILED or function error (code, surfaceId, message), which you can forward into a repair turn.
  • TypeScript
  • Python
  • Dart
Wire format: inbound action, callAgentFunction, and agentFunctionResponse

Below are the wire envelopes for an inbound action with synchronized data-model metadata in v1.0 and v0.9.1, plus the v1.0 callAgentFunction request and agentFunctionResponse reply:

v1.0 renderer_to_agent.json ↗ v1.0 renderer_data_model.json ↗ v1.0 AgentFunctionResponseMessage ↗ v0.9.1 client_to_server.json ↗ v0.9.1 client_data_model.json ↗
  • v1.0 (Candidate)
  • v0.9.1 (Active)

Step 6: Wire everything at the server entry point

Connect OrderAgentService from Steps 2 through 5 to an HTTP endpoint (POST /api/agent) that accepts initial prompts and client envelopes ({sessionId, prompt, message, metadata}), replies immediately to callAgentFunction RPCs with JSON, and streams validated A2UI messages over Server-Sent Events (text/event-stream):

  • TypeScript
  • Python
  • Dart

Connect to agent frameworks and transports

Instead of writing a custom HTTP route, you can plug A2uiGenerator and A2uiRequestProcessor into standard agent frameworks and protocols:

Google ADK

Install a2ui-adk (or "a2ui-adk[a2a]" when serving ADK over A2A) to bind per-session processors with A2uiProcessorStore, inject prompt instructions safely with A2uiInstruction, expose the send_a2ui_json_to_client tool via SendA2uiToClientToolset, and convert ADK events into A2A parts with A2uiEventConverter:

Avoid raw prompt strings in LlmAgent.instruction

ADK substitutes {name} placeholders in plain string instructions from session state. Concatenating processor.prompt_snippet into a raw LlmAgent.instruction string raises KeyError on A2UI braces (such as ${expression} or \\p{XID_Start}). Always wrap your instruction in A2uiInstruction, which resolves your own {store_city} template variables while leaving the A2UI prompt untouched.

A2A protocol

Install a2ui-a2a to advertise A2UI support on your AgentCard, negotiate the A2A Extension Specification per request, and wrap validated messages as application/a2ui+json DataPart payloads:

AG-UI and CopilotKit

To stream A2UI surfaces over AG-UI, enable the a2ui option on CopilotRuntime in @copilotkit/runtime. CopilotKit injects the A2UI generation tool and translates tool calls and state deltas into AG-UI events across Python and TypeScript backends, including Google ADK (ag_ui_adk), LangGraph (CopilotKitMiddleware), and AWS Strands (@ag-ui/aws-strands). See the CopilotKit A2UI documentation for full runtime setup:

For Model Context Protocol tool servers that attach interactive UI resources (ui://), see A2UI over MCP and MCP Integration Overview.

Reference: end-to-end agent session message flow

The sequence diagram below traces how a client renderer, your agent server, A2uiRequestProcessor, and the language model interact across a multi-turn session. On the initial turn, the server negotiates the client’s a2uiRendererCapabilities into a processor bound to the session’s RendererState, appends promptSnippet to the system prompt, and streams LLM chunks through openStream to emit validated createSurface, updateComponents, and updateDataModel messages. When the client sends a callAgentFunction message, the server executes the backend function directly and replies with agentFunctionResponse. When the client sends a user action with a2uiRendererDataModel metadata, the server runs a new LLM turn against the existing RendererState to update the surface in place.
